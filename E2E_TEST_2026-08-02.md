# Findings

## Blockers — the pipeline could not run at all

### B1. Every import crashes on `KeyError: 'recovery_tiers'` — **FIXED**
`pfas_pipeline/method_profiles.py:940`

```python
tiers = _profile_data_cache.get(method_id, {}).get("recovery_tiers", [])
if not tiers and method_id == "FDA_32PFAS":
    tiers = _DEFAULT_PROFILE_CACHE["FDA_32PFAS"]["recovery_tiers"]   # KeyError
```

`_DEFAULT_PROFILE_CACHE["FDA_32PFAS"]` has no `recovery_tiers` key (it carries
only `instrument_verification`, `qc_acceptance`, `associated_qc_types`,
`matrix_factors`). The live FDA profile's `recovery_tiers` is `[]`, so the
fallback fires and raises on **every** run, aborting `run_pipeline` inside
`RunQueue.auto_evaluate()`.

This is unconditional on the shipped configuration: no instrument file can be
processed. Fixed here by making the fallback a `.get(..., [])`, which is the
minimum to unblock. **The underlying cause is B18** — `recovery_tiers` is empty
because nothing ever seeds it.

### B2. No Import Studio profile can ever be found by the importer
`src/senaite/pfas/browser/import_studio.py:335` vs
`pfas_pipeline/vendor_profiles.py:151`

The two vendor detectors are documented as mirrors of each other and are not:

| | result for this file |
|---|---|
| `import_studio._detect_vendor_py27` (what the UI saves under) | `waters`, **confidence 12** |
| `vendor_profiles.detect_vendor` (what the importer looks up) | `native` |

Profiles are keyed `"{vendor_key}:{version}"`, so the UI wrote `waters:0.039`
and the importer asked for `native:0.039`:

```
GET @@pfas-instrument-profile?vendor_key=native&version=0.039
{"error": "No import mapping exists for FDA Native / Pass-through version 0.039"}
ImportError: … open Import Studio to create one.
```

Two aggravating factors:

* **The version key is scraped from sample data.** `detect_software_version`
  scans the first 20 lines for `\d+\.\d+` and matched `0.039` — a *concentration*
  in row 1's Sample Description. A file whose first row has a different
  concentration gets a different key and stops matching.
* **The suggested mapping corrupts a file that needs no mapping.** These headers
  already match `importer._COL_MAP` exactly, so the correct profile is the empty
  pass-through map. `_suggest_mapping` instead ignores 46 of 72 columns and
  mis-assigns others: `Response`→`response_ratio` (colliding with
  `Response Ratio`), `Concentration Units`→`measured_conc` (a unit string),
  `Expected RT`/`Observed RT`/`RT Relative to IS` all →`observed_rt`,
  `Calculated Concentration`→`measured_conc` so `calculated_conc` is never
  populated, and `Reporting Limit`, `Linked Internal Standard` and
  `Sample Description` dropped — which kills the BLoQ and SUR qualifiers.
  Duplicate rename targets collapse under `df.rename`, and `to_dict()` keeps
  only the last, so this is silent data loss.

*Test unblock (flagged, not a product fix):* a `native:0.039` profile with an
empty map was registered so the run could proceed.

## Correctness — wrong numbers reach the report

### B3. Dilution results are reported 10× high
`pfas_pipeline/pipeline.py:128,180` vs `pfas_pipeline/injection_store.py:98`

The file provides both `Measured Concentration` (raw curve reading) and
`Calculated Concentration` (× Sample Factor — the reportable value). Two modules
choose opposite precedence:

```python
# pipeline.build_summary        →  RAW
conc = row.measured_conc or row.calculated_conc
# injection_store               →  CORRECTED
_f(r.calculated_conc) if r.calculated_conc is not None else _f(r.measured_conc)
```

Proven against the instrument's own `Total` rows:

| Injection | Analyte | Pipeline | Instrument | Δ |
|---|---|---|---|---|
| Egg-1 Sample | PFOS | 1.5538708 | 1.5538708 | −5e−15 ✅ |
| Egg-1 Sample | PFHxS | 0.029714249 | 0.029714249 | −1e−17 ✅ |
| Egg-3 Sample | PFOS | 0.015766869 | 0.015766869 | −1e−17 ✅ |
| **Egg-3; Dil. 1:10** | **PFOS** | **1.3838746** | **0.13838746** | **+1.25 (×10)** |
| **Egg-4; Dil. 1:10** | **PFOS** | **1.6075694** | **0.16075694** | **+1.45 (×10)** |
| **Egg-4; Dil. 1:10** | **PFHxS** | **0.030666869** | **0.0030666869** | **+0.028 (×10)** |
| Egg-4 Sample | PFHxS | 0.00018825243 | *(no Total row)* | see below |

The last row is B3 and B4 interacting, and is the cleanest illustration that
these tokens carry meaning: both PFHxS isomers came back `BLoQ`, so the
instrument declined to emit a `Total` at all — and the pipeline produced a
number anyway.

Isomer summation itself is **exact** on every neat sample — `_sum_isomer_pair`
reproduces the instrument's `Total` to floating-point noise. The 10× error is
purely the column-precedence choice, and `Sample Factor` is never applied
anywhere in the pipeline.

Compounding it: the two `Dil. 1:10` injections classify as `Sample`, so Egg-3
and Egg-4 each appear **twice** in the summary — once neat, once at 10× — with
nothing marking which is reportable.

### B4. `BLoQ` is silently downgraded to `N.D.`
`pfas_pipeline/importer.py:98`

The instrument writes qualifier tokens into the concentration columns:

| token | occurrences |
|---|---|
| `BLoQ` (Calculated Concentration) | 72 |
| `<value> (ALoQ)` | 17 |
| `Not Detected` | 9 |
| `N/A` (Measured Concentration) | 44 |

`_parse_float` returns `None` for anything non-numeric, and `_ND_VALUES` does
not know these tokens. So a result the instrument says was **detected below the
quantitation limit** is reported by the LIMS as **not detected** — a materially
different statement under FDA/EPA reporting. `Not Detected` and `BLoQ` become
indistinguishable. `(ALoQ)` values survive only by accident, because the
parallel `Measured Concentration` cell happens to be clean.

### B5. The Qual/Quan check uses the wrong column and flags half the run
`pfas_pipeline/qc_engine.py:188-240`

`qual_quan_check` compares each injection's **`Response Ratio`** (analyte area ÷
IS area — a concentration proxy) against the **mean response ratio across all
10 calibration levels**, which span 20 → 0.039 ng/mL, a 512-fold range. Any
sample whose concentration differs from that arbitrary mean by >30% is flagged.

| | flags |
|---|---|
| Pipeline `(QQ)` flags raised | **658** of 1254 rows (52%) |
| A correct ±30% check on `Ion Ratios` vs `Expected Ion Ratios` | **23** of 497 (4.6%) |
| The instrument's own `Ion Ratio Check` column | 140 Fail / 599 Pass |

The file supplies `Ion Ratios`, `Expected Ion Ratios`, `Ion Ratio Tolerances (%)`,
`Ion Ratio Deviations (%)` **and** a Pass/Fail `Ion Ratio Check` verdict. None of
them is mapped in `_COL_MAP`. Real ion-ratio failures are invisible inside the
noise, and every sample shows "31 of 32 analytes flagged" in Data Review.

## Broken joins — data is recorded correctly and never reaches review

### B6. The traceability gate is empty even though every link was filled in
`src/senaite/pfas/browser/data_review.py:500-527`

Result: `direct_reagents=0 direct_standards=0 prepared_standards=0 unresolved=0`
— for a batch with 5 reagent lots, 5 prepared standards with parent chains, and
FM-ENV-251 lot references pointing at them. Two independent breaks:

1. **`_linked_batch()` can never resolve.** It reads `batch_id` out of the
   worksheet's CoC annotation, but the **CoC field schema has no `batch_id`
   field**, so nothing populates it. Logbooks 250/251/253 are written on the
   *Batch*; Data Review reads the *Worksheet* and then the CoC-linked batch —
   which is always `None`. The dual-read "find the data wherever the bench
   recorded it" therefore finds nothing.
2. **The guided extraction throws away what it collected.** Reagent lots and
   equipment S/Ns are captured per stage in the session, but
   `_handle_finalize` writes a logbook-252 stub containing only
   `analyst / extraction_date / method / from_guided / finalized_*`. The
   traceability tree reads `lb252["reagents"]` and `lb252["standards"]`, which
   the stub never writes.

This is the ISO 17025 §6.6 chain — CLAUDE.md §1.6 — and it is severed at both
ends.

### B7. The QC Summary gate has no data to read
Result: `{"error": "no_batch_record", "overall_pass": false}`.

The pipeline computed 1017 QC flags and persisted 1254 rows to
`injection_results`, but **nothing in the production path writes `qc_results` or
`calibrations`**. Verified rather than assumed:

* the only `INSERT INTO qc_results` outside `qc/store.py` is in
  `seed_calibrations.py`, and the only caller of `QCResultStore.add_result` is
  `seed_surrogate_recovery.py` — both seeding scripts;
* **`add_results_bulk` has no caller anywhere in the codebase**, despite
  `qc/control_chart.py:493` existing solely to build "list of dicts suitable for
  `QCResultStore.add_results_bulk()`". The wiring was never completed;
* the 304 pre-existing rows belong to `BATCH-COA-DEMO`, `WS-0001`, `WS-001` and
  six `B-2026-*` chart-demo batches — all seeded, none from an import.

So after a real import:

| table | rows for WS-0005 |
|---|---|
| `injection_results` | 1254 |
| `qc_results` | **0** |
| `calibrations` | **0** (570 CAL rows and per-analyte R² in the file) |

The QC Summary gate, the control charts and the Calibrations page are all empty
after a successful run.

### B8. No result reaches a SENAITE Analysis
`pfas_pipeline/pipeline.py:335-340`

The push loop keys on `validate_injection_name(...)["starlims_id"]`, a 7-digit
number, then `find_sample_by_starlims`. These injection names carry none, so
every sample result is dropped. Data Review's Final Data page confirms it: all
288 analyses show `result: ""`, state `assigned`.

Upstream of that, **8 of 20 injection names fail `INJECTION_PATTERNS`**
(`pfas_pipeline/constants.py:159`) — all 4 samples, both dilutions, the LFSM and
the LFSMD. Only CAL/CCV/MB match. The patterns are a hardcoded Python constant
encoding one naming convention (§1.1), and `run_pipeline` only logs a warning
before continuing into a push that cannot work.

### B9. Acquisition timestamps never parse
`pfas_pipeline/importer.py:107`

The file uses `Oct 08, 2025 17:55:21`; `_parse_datetime` tries only numeric
formats (`%Y-%m-%d`, `%d/%m/%Y`, `%m/%d/%Y`). Every row gets `dt = None`, so
`concat_id` degrades to the bare injection name and every one of the 1254
`injection_results` rows has `run_date = ''`. Run-date grouping, control charts
and time-based CCV bracketing have nothing to work with.

### B10. `batch_method()` returns the Zope id, and an unknown id yields a truthy empty profile
`data_review.py:139` + `method_profile_store.py:1043`

`batch_method()` returns `m.getId()` → `'method-1'`, but profiles are keyed by
`Method.MethodID` → `'FDA_32PFAS'`. `get_profile(portal, 'method-1')` then
returns `{"method_id": "method-1"}` — **truthy**, so every `if profile:` caller
proceeds with no `r2_min`, no CCV window, no recovery tiers and no acceptance
criteria. The failure is completely silent. `method_bridge.get_method_cal_code`
already resolves `MethodID` correctly; Data Review does not use it.

## Identity and naming

### B11. The Run Builder emits a worklist the LIMS itself rejects
All **27 of 27** generated injection names fail `validate_injection_name`:

```
PS-KCP-CAL-251006-L1 … -L10, PS-KCP-CAL-251006-ICV, FDA_32PFAS-CCB-260803-01,
FDA_32PFAS-FEED-0002 …, PS-KCP-SPK-251020-LFSM, PS-KCP-SPK-251020-LFSMD
```

The bracketing logic itself is **correct** — calibrators, then ICV and solvent
blank outside the bracket, CCV opening the body, samples every 6, LFSM/LFSMD,
closing CCV — and the prepared-standard lot codes are carried through. But the
names can never round-trip: the analyst types `KCP Silage "Egg-1" Sample` into
the instrument, the builder proposes `FDA_32PFAS-FEED-0002`, and the validator
accepts neither.

### B12. The worklist asserts a wrong preparation date
`PS-KCP-SPK-251020` was prepared 2025-10-20; its worklist description says
`prep 2025-10-06`. `build_sequence` takes a single `prepared_date` from
FM-ENV-251 and stamps it on every QC injection regardless of which lot the row
names — while the PreparedStandard object holds the correct date. The LFSM/LFSMD
names also drop the parent sample identity that the extraction pedigree records.

### B13. The two Data Review pages disagree on what an analyte is called
The injection-level page reports `10:2 FTS`, `4:2 FTS`, `GenX (HFPO-DA)` (display
names, from `injection_results`); the Final Data page reports `10:2FTS`,
`4:2FTS`, `GenX` (SENAITE keywords). An analyst cannot cross-reference the two.

Note for the record: the predicted *summary-level* name mismatch did **not**
occur — the profile store exports `display_analyte_set`, so
`build_summary` matches the instrument's display names correctly. The
keyword/display split bites at the Data Review boundary instead.

### B14. The connector creates a second Batch named after the worksheet
Data Review joins `injection_results` on the **Worksheet** id, so
`run_pipeline(batch_id=...)` must be given `WS-0005`. `SenaiteConnector.create_batch`
then searches for a Batch titled `WS-0005`, finds none, and creates one —
alongside the real `kcp-b-001`. The two identifiers are in direct conflict.

Related: `run_worker.py` (the watcher, the only production entry point) passes no
`batch_id`, `method_id`, `matrix` or `client_uid` at all, so an
automatically-watched file defaults `batch_id` to the CSV filename stem and runs
with an empty method — nothing it produces can reach Data Review.

## Compliance

### B15. The EDD exports 288 rows with no results and does not block
`@@pfas-egad-export?batch_id=kcp-b-001&action=download` returns 200 and a
60 kB CSV — 288 rows, **every `CONCENTRATION` empty**, because of B8. CLAUDE.md
§3 requires the EDD to block when an analyte lacks a CAS; there is no equivalent
guard for missing results, so a regulator-bound file with blank concentrations
generates cleanly.

`SAMPLE_TYPE` is emitted as `GW` (groundwater) for an Animal Feed sample. Not
hardcoded in the writer — `egad_publish.get_ar_sample_type(ar, default="GW")`
reads a per-sample `senaite.pfas.egad_sample_type` annotation set at intake, and
falls back to groundwater when it is unset. So the defect is that nothing in the
sample-creation path derives the EGAD code from the sample's own SampleType, and
the fallback is a specific wrong matrix rather than a blocking blank.

### B16. Attachment upload fails — wrong container, not authentication
`ERROR Attachment upload failed: 401 Client Error: Unauthorized`. The 401 is
misleading: the same authenticated session created the Batch seconds earlier.
The API body says what actually happened:

```
POST @@API/senaite/v1/create {"portal_type": "Attachment", "parent_uid": <batch>}
401 {"message": "Creation of 'Attachment' in '/senaite/batches/kcp-b-001' is not allowed"}
```

`SenaiteConnector.attach_file` (`senaite_connector.py:184`) posts the Attachment
with the **Batch** as `parent_uid`, and a Batch is not a permitted container for
Attachment in SENAITE 2.6. The batch report PDF is generated
(`/data/reports/WS-0005_report.pdf`) but never attached, so the Instrument Report
gate has nothing to point at. Fix is a container change, not a credential one.

### B18. `recovery_tiers` is never seeded, so the no-labeled-standard tier does not exist
This is what B1's crash was standing on top of, and it outlives the fix.

`recovery_tiers` appears in **no** `DEFAULT_PROFILES` entry in
`method_profile_store.py`. Its only writer is the Method Profile UI's raw-JSON
`recovery_tiers_json` textarea (`browser/method_profiles.py:729`). Nobody has
ever typed into that box, so it is `[]` on every method.

Consequences, all silent:

* `get_non_iso_set()` returns `frozenset()`, so `is_non_iso` is False for every
  analyte and `build_summary` never applies the `N.C.` qualifier from that path.
  (The 33 `(N.C.)` flags observed come from a *different* rule —
  `qc_engine.py:477`, S/N < 3 — which is why the crash was not obviously
  changing any output.)
* The FDA tier CLAUDE.md §3 describes — **40–140% + RSDr ≤ 30% for analytes with
  no commercially matched labeled standard** — has no representation at all, so
  LFSM/LFSMD recovery for PFODA, PFPeS, PFHpS, PFNS, PFDS, PFDoS, PFTrDS,
  PFUnDS, DONA and PFTrDA is judged against the wrong tier.

Underneath this is a §1.3 duplication: the same regulatory concept exists twice,
as the seeded, structured `qc_acceptance.tiers` (which *does* carry
`tier3_no_std`, 40–140%, RSD 30%) and as the unseeded free-JSON
`recovery_tiers`. `analyte_reference.NATIVE_ANALYTES[7]` (`no_labeled`) already
holds the analyte membership authoritatively. Three representations, one truth.

### B19. The empty-gate states misdirect the analyst
Screenshots: `dr_gates.png`, `dr_trace.png`, `dr_qc.png`.

The page itself renders cleanly — no crash, no blank panel — but:

* **Traceability** says *"No traceability data found. Ensure FM-ENV-251 and
  FM-ENV-252 logbooks are filled in for this worksheet."* They **are** filled
  in. The logbook UI writes them on the Batch; Data Review looks on the
  Worksheet. The analyst is told to redo work they have done, and the offered
  *Open FM-ENV-251* button leads to the worksheet-scoped copy, which would
  create a second, divergent record.
* **QC Summary** shows the analyst a raw internal token: *"QC data unavailable:
  no_batch_record."*
* The header badge next to `WS-0005` reads **`METHOD-1`** — B10 visible on
  screen; an analyst has no way to tell that the method resolved to a Zope id
  and that every QC criterion is therefore empty.
* On the Overview, both AUTO gates sit at red `PENDING` with no reason and no
  action, while the manual gates offer *Sign & Mark Reviewed*. The two failures
  that matter are the two the analyst cannot act on.

### B17. Prepared standards expire retroactively — needs a decision
The CAL lot was prepared 2025-10-06 with a 6-month expiry, correct for a run on
2025-10-20. Read today (2026-08-02) all five KCP standards report `expired`,
because `_is_expired` compares against *now* rather than against the date of
use. ISO 17025 asks whether the standard was in date **when used**; as written, a
historical batch becomes progressively less defensible the longer it sits.
Flagging rather than filing — this may be intended.
